# 신입사원 김넵 키우기 — 제품 및 구현 기획서

> 문서 버전: v1.0  
> 목표 플랫폼: 세로형 모바일 웹  
> 1회 플레이 목표 시간: 약 5분  
> 확정 기술 스택: **Next.js(App Router) + TypeScript + Tailwind CSS**

## 0. 확정안 요약

- 플레이어는 가상의 신입사원 **김넵**이 되어 5일 동안 하루 3개씩, 총 15개의 메신저 상황에 답한다.
- 선택지는 상황마다 3~4개이며, 선택 즉시 짧은 결과 설명과 능력치 변화를 보여준다.
- 핵심 능력치는 `눈치력`, `업무력`, `멘탈`, `상사 호감도`, `퇴근 가능성`의 5개다.
- 모든 능력치는 0~100이며 시작값은 50이다. 선택 결과를 더한 뒤 매번 0~100 범위로 제한한다.
- 하루의 세 문제를 마치면 규칙 기반의 일일 분석을 제공한다. 화면과 데이터 계층을 분리해 추후 OpenAI API 분석으로 교체할 수 있게 한다.
- 5일차 종료 후 우선순위가 명확한 규칙으로 4개 엔딩 중 하나를 결정한다.
- 로그인·서버·결제·랭킹·소셜 공유·자유 입력·실시간 AI는 1차 버전에 넣지 않는다.
- 게임 데이터와 분석 문구는 로컬 TypeScript 데이터 파일에 두고, 진행 상태만 `localStorage`에 저장한다.
- 비주얼과 문항의 최신 방향은 이 문서의 **1.9 캐릭터·아트 디렉션**과 **5.1 15개 문제 구성**을 단일 기준으로 삼는다. 초기의 평범한 회사원 캐릭터와 상식 퀴즈형 연출은 사용하지 않는다.

## 1. PRD

### 1.1 제품 개요

**신입사원 김넵 키우기**는 직장에서 자주 쓰이는 애매한 표현의 숨은 의미를 가볍게 해석하고, 적절한 답변을 고르며 가상의 신입사원을 성장시키는 선택형 직장생활 시뮬레이션 게임이다. 정답 암기보다 “상황과 관계에 따라 말의 온도가 달라진다”는 재미를 전달한다.

### 1.2 해결하려는 문제

- 사회초년생은 완곡한 업무 표현을 문자 그대로 받아들여 대응 시점이나 말투를 판단하기 어렵다.
- 직장 커뮤니케이션 콘텐츠는 설명 위주인 경우가 많아 짧게 몰입하고 반복하기 어렵다.
- 사용자는 실제 회사에서 실수하지 않고도 여러 답변의 결과를 안전하고 유쾌하게 경험하고 싶다.

### 1.3 목표 사용자

- 취업을 준비하거나 첫 직장에 입사한 지 얼마 되지 않은 20~30대
- 회사 메신저의 말투와 암묵적인 표현을 재미있게 체험하고 싶은 사용자
- 별도 설치나 가입 없이 5분 안에 끝나는 캐주얼 게임을 선호하는 사용자

### 1.4 제품 목표

1. 첫 방문자가 설명을 길게 읽지 않아도 30초 안에 첫 선택을 한다.
2. 한 판을 약 5분 안에 끝내고 엔딩까지 볼 수 있다.
3. 선택 직후 수치와 해설을 통해 결과를 명확히 이해한다.
4. 새 게임과 이어하기가 모두 안정적으로 동작한다.
5. AI API가 없어도 완결된 경험을 제공하고, 추후 분석 모듈만 교체할 수 있다.

### 1.5 핵심 경험 원칙

- **짧고 선명하게:** 한 화면에는 한 가지 핵심 행동만 둔다.
- **웃기지만 모욕적이지 않게:** 직장 밈을 활용하되 특정 세대·직급·직군을 비하하지 않는다.
- **맥락을 설명하기:** 결과를 단순 정답/오답이 아니라 상대가 어떻게 받아들일 수 있는지로 설명한다.
- **수치 변화는 예측 가능하게:** 같은 선택은 언제나 같은 결과를 내며 숨은 확률 요소는 없다.
- **모바일 우선:** 360~430px 너비에서 엄지손가락으로 편하게 플레이할 수 있어야 한다.

### 1.6 1차 버전 범위

#### 포함

- 시작, 게임 방법, 새 게임, 이어하기
- 고정 순서 15문제와 문제별 3~4개 선택지
- 선택 결과, 능력치 변화, 하루 종료 분석
- 5개 능력치, 4개 엔딩, 최종 리포트
- 로컬 저장, 처음부터 다시 하기
- 효과음 켜기/끄기(기본 꺼짐) 대신 **1차 버전에서는 소리 기능 자체를 제외**
- 키보드 조작과 기본 접근성

#### 제외

- 회원가입, 서버 DB, 클라우드 동기화
- 실제 AI 호출, 자유 입력형 답변, 챗봇
- 사용자 제작 문제, 랜덤 문제, 난이도 선택
- 친구 초대, 공유 이미지 생성, 랭킹, 업적, 상점
- 애니메이션 캐릭터 육성방, 아이템, 광고, 결제

### 1.7 콘텐츠 원칙

- 실제 인물, 회사, 부서, 브랜드 이름을 사용하지 않는다.
- 등장인물은 `선배`, `팀 리더`, `동료`, `협업 담당자`처럼 일반 명칭을 쓴다.
- “이 표현은 언제나 이런 뜻”이라고 단정하지 않고, 현재 제시된 맥락에서의 해석임을 결과 문구에 반영한다.
- 위협, 괴롭힘, 차별을 웃음의 소재로 정당화하지 않는다.

### 1.8 성공 기준

초기에는 분석 도구를 붙이지 않으므로 출시 전 수동 검수 기준으로 판단한다.

- 15문제와 4개 엔딩을 모두 오류 없이 확인할 수 있다.
- 새로고침 후 마지막 완료 지점부터 이어진다.
- 저장 데이터가 깨졌거나 이전 버전이어도 시작 화면으로 안전하게 복구한다.
- 360×800, 390×844, 430×932 화면에서 가로 스크롤이 생기지 않는다.
- 주요 흐름을 키보드만으로 완료할 수 있고 색상 외에도 수치 변화가 표시된다.

### 1.9 캐릭터·아트 디렉션

#### 한 줄 콘셉트

**“메신저 이모지가 살아 움직이는, 말랑한 신입사원 생존 코미디.”** 현실적인 정장 회사원이나 2010년대식 플랫 벡터 대신, 작은 화면에서 표정이 먼저 읽히는 스티커형 캐릭터를 사용한다.

#### 김넵 디자인 확정안

- **실루엣:** 머리가 몸의 약 55%를 차지하는 2.5등신, 둥근 사각형 얼굴, 짧은 팔·다리의 젤리 같은 형태
- **시그니처:** 머리 위에 작은 `N` 모양 안테나 한 가닥. 감정에 따라 `!`, `?`, 배터리 부족 모양으로 변한다.
- **얼굴:** 점눈과 한 줄 입을 기본으로 하고, 당황할 때 눈 밑에 작은 로딩 점 세 개가 나타난다.
- **의상:** 검정 정장 대신 라임색 후드 집업과 짙은 남색 사원증 스트랩. 회사 이름이나 부서명은 넣지 않는다.
- **소품:** 스마트폰, 식은 커피, 노트북만 사용한다. 서류가방·넥타이·빌딩 숲은 핵심 비주얼에서 제외한다.
- **색상:** 잉크 네이비 `#172033`, 김넵 라임 `#C9F56A`, 메신저 민트 `#6EE7C7`, 경고 코랄 `#FF7A72`, 배경 크림 `#FFF9ED`
- **질감:** 2px 안팎의 손그림 외곽선, 아주 약한 종이 노이즈, 둥근 그림자. 과한 3D 광택과 기업용 스톡 일러스트 느낌은 금지한다.

#### 감정 상태 6종

| 상태 | 표정·포즈 | 사용 지점 |
|---|---|---|
| 출근 전 | 한쪽 눈만 뜨고 커피를 든 자세 | 시작 화면 |
| 긴장 | 안테나가 `?`가 되고 휴대폰을 양손으로 잡음 | 선택 전 |
| 센스 | 안테나가 `!`가 되고 작은 반짝임 표시 | 센스 있는 대응 |
| 무난 | 엄지를 작게 들고 옅은 미소 | 무난한 대응 |
| 당황 | 로딩 점 눈물과 구겨진 후드 | 아쉬운 대응 |
| 멘붕 | 안테나가 배터리 1칸, 바닥에 납작해짐 | 위험한 대응 |

#### UI 적용 규칙

- 캐릭터는 시작·결과·엔딩의 감정 전달에만 사용하고, 문제 본문을 가리키는 장식으로 남용하지 않는다.
- 결과 모션은 0.4초 이내의 한 번 튕김 또는 납작해짐으로 제한하고 `prefers-reduced-motion`에서는 정지 이미지로 대체한다.
- 아바타는 48px에서도 안테나와 표정이 구분되어야 한다. 텍스트를 이미지 안에 넣지 않는다.
- 이미지 생성 도구를 쓸 경우 동일한 정면 기준 시트 한 장을 먼저 확정하고, 이후 포즈는 그 시트를 참조해 일관성을 유지한다.
- 최종 캐릭터는 특정 메신저 서비스의 스티커나 기존 캐릭터를 모방하지 않고 독자적인 실루엣을 가져야 한다.

#### 이미지 제작용 기준 프롬프트

#### 노후해 보이지 않게 하는 금지 목록

- 사실적인 정장 남성, 악수·상승 화살표·빌딩 같은 기업 스톡 이미지
- 큰 머리와 작은 몸만 적용한 흔한 벡터 회사원 템플릿
- 회색·파랑만 사용한 사내 시스템 화면, 유리 질감 카드의 과도한 사용

## 2. 사용자 흐름

### 2.1 첫 방문

1. 사용자가 시작 화면에 진입한다.
2. `게임 시작`을 누른다.
3. 3장짜리 간단 안내에서 게임 방식과 능력치를 확인한다.
4. `출근하기`를 누르면 1일차 첫 문제로 이동한다.
5. 상황 메시지를 읽고 답변 하나를 선택한다.
6. 선택 버튼이 잠기고 결과 패널에서 해석, 상대 반응, 능력치 변화를 확인한다.
7. `다음 메시지`를 눌러 다음 문제로 이동한다.
8. 하루 3문제를 끝내면 일일 리포트를 확인한다.
9. `다음 날 출근하기`를 눌러 다음 날을 시작한다.
10. 5일차 일일 리포트 후 `수습평가 확인하기`를 누른다.
11. 엔딩과 최종 능력치, 플레이 요약을 확인한다.
12. `처음부터 다시 하기`를 누르면 확인 절차 후 저장 데이터를 초기화하고 시작 화면으로 간다.

### 2.2 재방문

1. 유효한 미완료 저장 데이터가 있으면 시작 화면에 `이어하기`와 `새 게임`을 함께 표시한다.
2. `이어하기`는 저장된 문제 또는 결과 확인 상태로 복귀한다.
3. `새 게임`은 확인 모달을 거쳐 기존 진행을 지운 후 안내 화면부터 시작한다.
4. 이미 엔딩을 본 저장 데이터가 있으면 `결과 다시 보기`와 `새 게임`을 표시한다.

### 2.3 예외 흐름

- 저장 데이터 파싱 실패, 버전 불일치, 필수 필드 누락 시 해당 데이터를 삭제하고 “저장된 진행을 불러오지 못해 새 게임으로 시작합니다” 토스트를 한 번 표시한다.
- 문제 화면을 새로고침해도 이미 선택한 답을 다시 고를 수 없다. 결과 패널이 그대로 복원된다.
- 브라우저의 뒤로 가기로 과거 문제를 수정할 수 없게 게임 진행은 단일 게임 경로 안에서 상태로 제어한다.

## 3. 전체 화면 목록

| 번호 | 화면 | 경로 | 목적 |
|---|---|---|---|
| 1 | 시작 화면 | `/` | 게임 소개, 시작·이어하기·결과 보기 진입 |
| 2 | 게임 방법 | `/how-to-play` | 규칙과 능력치의 짧은 온보딩 |
| 3 | 게임 플레이 | `/play` | 상황 확인, 답변 선택, 결과 피드백 |
| 4 | 하루 종료 리포트 | `/day-result` | 당일 선택과 변화 요약, 규칙 기반 분석 |
| 5 | 수습평가 엔딩 | `/ending` | 최종 엔딩, 능력치, 총평, 재시작 |

별도 설정 페이지, 로딩 페이지, 오류 페이지는 만들지 않는다. 확인 모달과 토스트는 현재 화면 위에 표시한다.

## 4. 화면별 UI 구성요소

### 4.1 공통 레이아웃

- 최대 너비 430px의 중앙 정렬 앱 컨테이너, 최소 높이 `100dvh`
- 상단: 게임 로고 텍스트와 현재 일차(플레이 중에만 표시)
- 본문: 세로 스크롤 가능
- 하단 행동 영역: 주요 버튼이 화면 아래에 안정적으로 위치하되 작은 화면에서는 콘텐츠를 가리지 않음
- 주요 버튼 최소 높이 48px, 터치 영역 간격 최소 8px
- 색상은 밝은 메신저 톤을 기본으로 하며 본문 대비는 WCAG AA 수준을 목표로 함
- 능력치별 색은 보조 수단이며 항상 아이콘/이름/숫자를 함께 표시

### 4.2 시작 화면

- 제목 `신입사원 김넵 키우기`
- 한 줄 소개 `회사어를 해석하고 무사히 수습을 통과하세요.`
- 김넵의 정적인 캐릭터 일러스트 또는 CSS 기반 아바타 자리
- 예상 시간 `약 5분 · 총 15문제`
- 저장 상태별 주요 행동
  - 저장 없음: `게임 시작`
  - 진행 중: `이어하기`(주요), `새 게임`(보조)
  - 완료: `결과 다시 보기`(주요), `새 게임`(보조)
- 하단 주의 문구 `모든 상황과 인물은 가상이며, 해석은 맥락에 따라 달라질 수 있습니다.`

### 4.3 게임 방법 화면

- 페이지 표시 `1/3`, `2/3`, `3/3`
- 카드 1: 메신저 상황을 읽고 답변 선택
- 카드 2: 5개 능력치 설명
  - 눈치력: 말의 의도와 분위기를 읽는 힘
  - 업무력: 우선순위를 잡고 결과물을 만드는 힘
  - 멘탈: 당황하지 않고 버티는 힘
  - 상사 호감도: 팀 리더가 느끼는 신뢰와 편안함
  - 퇴근 가능성: 오늘 제시간에 퇴근할 여유
- 카드 3: 하루 3문제, 총 5일과 수습평가 안내
- `이전`, `다음`, 마지막 장의 `출근하기` 버튼
- 온보딩을 건너뛰는 버튼은 두지 않아 첫 플레이 규칙을 확실히 전달

### 4.4 게임 플레이 화면

- 상단 진행 정보: `DAY 1`, `1/15`, 전체 진행 바
- 접을 수 없는 미니 능력치 바 5개(현재 수치만 간결히 표시)
- 메신저 카드
  - 발신자 역할과 가상 아바타
  - 시간
  - 상황 설명(필요한 경우)
  - 핵심 메시지 말풍선
- 질문 문구 `김넵은 뭐라고 답할까?`
- 답변 선택지 3~4개, 원문 전체가 보이는 세로 버튼
- 선택 전에는 주요 다음 버튼을 표시하지 않음
- 선택 후
  - 고른 답을 강조 표시(다른 선택지도 눌러 답을 바꿀 수 있음)
  - 결과 패널: 결과 라벨, 회사어 해석, 상대 반응, 한 줄 팁
  - 변화 칩: `눈치력 +5`, `멘탈 -3`처럼 0이 아닌 항목만 표시
  - 변화 후 능력치 바를 갱신
  - `다음 메시지` 또는 세 번째 문제일 때 `오늘 업무 마치기`
- “정답/오답” 표현은 사용하지 않고 `센스 있는 대응`, `무난한 대응`, `아쉬운 대응`, `위험한 대응`의 4단계 결과 라벨 사용

### 4.5 하루 종료 리포트 화면

- 헤더 `DAY N 업무 종료`
- 오늘의 대표 평가 배지(아래 분석 규칙으로 결정)
- 오늘 변화량 5개: 시작 수치 → 종료 수치와 증감
- 규칙 기반 분석 카드
  - 잘한 점 1개
  - 주의할 점 1개
  - 내일의 팁 1개
- 오늘의 답변 3개를 접힌 목록으로 표시(상황 제목, 고른 답, 결과 라벨)
- `다음 날 출근하기` 또는 5일차의 `수습평가 확인하기`
- AI라는 표현은 1차 버전 UI에서 쓰지 않는다. 추후 API 연결 시 `AI 코치 분석` 라벨을 추가할 수 있다.

### 4.6 수습평가 엔딩 화면

- 엔딩 등급과 제목
- 엔딩 일러스트/이모지
- 2~3문장의 스토리 결과
- 최종 능력치 5개와 종합점수
- 강점: 가장 높은 능력치(동점 시 고정 우선순위 적용)
- 성장 포인트: 가장 낮은 능력치(동점 시 고정 우선순위 적용)
- 플레이 요약: 센스/무난/아쉬움/위험 대응 횟수
- `처음부터 다시 하기` 버튼과 확인 모달
- 공유 기능은 1차 버전에서 제외

## 5. 게임 규칙

1. 게임은 5일로 구성되며 하루에 3문제, 총 15문제를 고정된 순서로 진행한다.
2. 각 문제에는 3~4개의 답변이 있고 하나만 선택할 수 있다.
3. 다음 문제로 넘어가기 전까지는 다른 선택지로 자유롭게 바꿀 수 있으며, 능력치는 선택할 때마다 초기값부터 다시 계산해 항상 정확하게 반영한다. 다음 문제로 이동하면 그 답변은 확정된다.
4. 선택에는 결과 라벨, 설명, 5개 능력치 변화량이 미리 정해져 있다.
5. 숨은 확률, 제한 시간, 실패로 인한 중도 게임 오버는 없다.
6. 능력치가 0이 되어도 게임은 계속되며 최종 엔딩 판정에만 영향을 준다.
7. 모든 문제를 완료하면 반드시 4개 엔딩 중 하나를 본다.
8. 문제 순서를 고정해 첫 버전의 밸런스 검수와 오류 재현을 쉽게 한다.
9. 저장은 온보딩 완료, 답변 선택, 다음 문제 이동, 일일 리포트 진입, 엔딩 결정 시점마다 수행한다.
10. 새 게임을 시작하면 기존 선택 기록과 능력치를 모두 초기화한다.

#### 선택지 집필 규칙

- 선택지는 3개를 기본으로 하고, 정말 다른 전략이 네 가지일 때만 4개를 쓴다.
- 모든 선택지는 현실에서 한 번쯤 누르고 싶은 유혹이 있어야 한다. 하나만 문법적으로 완벽하게 길게 쓰지 않는다.
- 황당한 선택지도 현실의 감정에서 출발해야 하며, 무작위 개그나 타인에게 무례한 행동만으로 웃기지 않는다.
- 결과 첫 문장은 25자 안팎의 메신저 리액션처럼 쓰고, 설명은 `왜 웃긴지`가 아니라 `상대가 어떻게 이해했는지`를 알려준다.
- 밈과 유행어는 출시 시점에 빠르게 낡으므로 고유 밈 대신 타이핑 중, 읽음, 파일명, 알림 시간 같은 오래가는 디지털 직장 디테일을 활용한다.
- 최선 선택이 늘 확인 질문은 아니다. 긴급 상황에서는 즉시 공유, 사소한 상황에서는 짧은 결정처럼 행동의 리듬을 바꾼다.

#### 재미 검증 기준

문항별로 내부 3인 이상이 아래 항목을 1~5점으로 평가한다. 평균 3점 미만 항목이 있으면 문구를 다시 쓴다.

1. 첫 두 문장만 읽어도 상황이 그려지는가?
2. 최소 두 선택지 사이에서 2초 이상 고민하게 되는가?
3. 결과를 보기 위해 다른 선택지도 눌러 보고 싶은가?
4. 특정 집단을 조롱하지 않고도 웃긴가?
5. 결과 해설에서 실제 커뮤니케이션 힌트를 하나 얻는가?

문항은 직장 내 유일한 정답을 가르치기보다 확인 질문, 우선순위 합의, 책임 있는 보고가 대체로 좋은 결과를 만든다는 방향으로 작성한다.

## 6. 능력치 계산 규칙

### 6.1 기본 계산

- 5개 능력치의 시작값은 모두 `50`이다.
- 각 선택의 변화량은 능력치별 `-10`부터 `+10`까지의 정수다.
- 한 선택에서 변경되는 능력치는 2~4개로 제한하고, 모든 변화량이 0인 선택은 만들지 않는다.
- 새 수치 계산식: `현재 수치 + 선택 변화량`, 이후 0 미만은 0, 100 초과는 100으로 제한한다.
- 화면에 표시하는 수치와 엔딩 계산에 사용하는 수치는 같은 정수다.
- 하루 종료 보너스, 연속 선택 보너스, 랜덤 보정은 없다.

### 6.2 선택지 밸런스 기준

| 결과 라벨 | 권장 총 변화량 | 설계 의미 |
|---|---:|---|
| 센스 있는 대응 | +10 ~ +18 | 맥락 파악과 실행을 모두 잘한 선택 |
| 무난한 대응 | +3 ~ +9 | 큰 문제는 없지만 최선은 아닌 선택 |
| 아쉬운 대응 | -3 ~ +2 | 일부 장점과 분명한 단점이 함께 있는 선택 |
| 위험한 대응 | -12 ~ -4 | 관계나 업무에 뚜렷한 위험이 있는 선택 |

`총 변화량`은 다섯 변화량의 단순 합이다. 좋은 선택에도 멘탈이나 퇴근 가능성이 조금 줄 수 있으며, 나쁜 선택에도 당장의 퇴근 가능성이 오를 수 있다. 다만 결과 라벨과 총 변화량 범위는 일치해야 한다.

### 6.3 종합점수

- 최종 종합점수는 다섯 능력치의 산술평균을 반올림한 0~100 정수다.
- 엔딩 1차 판정에는 개별 능력치와 위험 대응 횟수를 사용하고, 종합점수는 그다음 판정에 사용한다.
- 강점/성장 포인트 동점 우선순위는 `눈치력 → 업무력 → 멘탈 → 상사 호감도 → 퇴근 가능성`으로 고정한다.

### 6.4 일일 분석 규칙

1. 그날 합산 변화량이 가장 큰 능력치를 잘한 점으로 선택한다.
2. 그날 합산 변화량이 가장 작은 능력치를 주의할 점으로 선택한다.
3. 동점이면 능력치 고정 우선순위를 사용한다.
4. 당일 `위험한 대응`이 있으면 결과 문구 중 해당 선택의 팁을 내일의 팁으로 우선 사용한다.
5. 위험 대응이 없으면 가장 낮은 능력치에 대응하는 미리 작성된 팁을 사용한다.
6. 하루 대표 평가 배지는 그날 결과 중 가장 많이 나온 라벨을 쓰고, 동점이면 더 낮은 라벨을 사용해 과도한 칭찬을 피한다.

## 7. 문제 데이터 구조

구현 데이터는 `src/data/questions.ts`에 저장한다. 타입 정의는 `src/types/game.ts`에 분리한다. 아래는 구현자가 따라야 할 필드 명세이며 실제 코드는 아니다.

### 7.1 문제 필드

| 필드 | 타입 | 필수 | 설명 |
|---|---|---:|---|
| `id` | 문자열 | 예 | 고유 ID. `day1-q1` 형식 |
| `day` | 1~5 정수 | 예 | 소속 일차 |
| `order` | 1~15 정수 | 예 | 전체 진행 순서, 중복 없음 |
| `title` | 문자열 | 예 | 기록 목록에 표시할 짧은 상황명 |
| `context` | 문자열 | 예 | 메시지 전 상황 설명, 1~2문장 |
| `senderRole` | 문자열 | 예 | `팀 리더`, `선배`, `동료` 등 일반 역할명 |
| `sentAt` | 문자열 | 예 | 연출용 시각, `17:47` 형식 |
| `message` | 문자열 | 예 | 받은 메신저 내용 |
| `prompt` | 문자열 | 예 | 사용자에게 묻는 문장 |
| `choices` | 선택지 배열 | 예 | 3~4개, 표시 순서대로 저장 |

### 7.2 선택지 필드

| 필드 | 타입 | 필수 | 설명 |
|---|---|---:|---|
| `id` | 문자열 | 예 | 문제 안에서 고유한 ID. `a`, `b`, `c`, `d` |
| `text` | 문자열 | 예 | 사용자가 고르는 답변 원문 |
| `resultLabel` | 열거형 | 예 | `great`, `safe`, `awkward`, `risky` 중 하나 |
| `interpretation` | 문자열 | 예 | 이 상황의 회사어 해석 |
| `reaction` | 문자열 | 예 | 선택 후 상대 반응 또는 결과 |
| `tip` | 문자열 | 예 | 다음에 활용할 한 줄 팁 |
| `statChanges` | 능력치 변화 객체 | 예 | 5개 능력치의 정수 변화량, 미변경은 0 |

### 7.3 능력치 키

| 화면 이름 | 데이터 키 |
|---|---|
| 눈치력 | `sense` |
| 업무력 | `work` |
| 멘탈 | `mental` |
| 상사 호감도 | `favor` |
| 퇴근 가능성 | `leaveChance` |

### 7.4 저장 상태 필드

`localStorage` 키는 `kimnep-game-save-v1`로 고정한다.

| 필드 | 설명 |
|---|---|
| `version` | 저장 형식 버전. 초기값 1 |
| `status` | `playing`, `dayResult`, `completed` 중 하나 |
| `onboardingCompleted` | 온보딩 완료 여부 |
| `currentQuestionIndex` | 0부터 시작하는 현재 문제 위치 |
| `stats` | 현재 5개 능력치 |
| `dayStartStats` | 현재 일차 시작 시점의 능력치 |
| `answers` | 문제 ID, 선택지 ID, 결과 라벨, 적용 변화량 기록 배열 |
| `selectedChoiceId` | 현재 문제에서 답을 골랐다면 선택지 ID, 아니면 없음 |
| `endingId` | 완료된 경우 결정된 엔딩 ID |
| `updatedAt` | 마지막 저장 시각의 ISO 문자열 |

저장할 때 데이터 전체를 교체한다. 불러올 때 버전과 필수 필드, 인덱스 범위를 검증한다. UI 문구나 전체 문제 본문은 저장하지 않고 ID만 저장해 중복과 불일치를 줄인다.

### 7.5 분석 모듈 경계

- 화면은 `GameAnalysis`라는 공통 결과 형태만 사용한다: 제목, 잘한 점, 주의할 점, 다음 팁.
- 1차 버전의 `localAnalyzer`는 위 일일 분석 규칙과 미리 작성된 문구로 결과를 만든다.
- 추후 `openAiAnalyzer`가 같은 결과 형태를 반환하도록 추가한다.
- 화면 컴포넌트가 API를 직접 호출하지 않으며, API 키를 브라우저 코드나 로컬 저장소에 넣지 않는다.
- API 도입 전까지 `localAnalyzer`만 활성화하며 네트워크 실패 처리 UI는 만들지 않는다.

## 8. 엔딩 조건

엔딩은 아래 표를 **위에서 아래 순서로 최초 일치하는 하나**로 결정한다. 이 우선순위 때문에 조건이 겹쳐도 결과가 항상 동일하다.

| 우선순위 | ID / 제목 | 조건 | 방향 |
|---:|---|---|---|
| 1 | `ending-survival` / 조용한 생존자 | 능력치 중 하나라도 25 이하 **또는** 위험한 대응 5회 이상 | 수습은 통과했지만 기본기 보완이 필요하다. 실패 엔딩 대신 재도전을 유도한다. |
| 2 | `ending-ace` / 눈치백단 에이스 | 종합점수 75 이상, 눈치력 70 이상, 업무력 70 이상, 능력치 모두 50 이상 | 일과 관계의 균형을 갖춘 최고 엔딩이다. |
| 3 | `ending-trusted` / 믿고 맡기는 신입 | 업무력 70 이상 **또는** 상사 호감도 70 이상 | 결과와 신뢰 중 하나가 뚜렷한 안정적 통과 엔딩이다. |
| 4 | `ending-my-pace` / 마이웨이 성장형 | 위 조건에 해당하지 않음 | 아직 서툴지만 자기 방식으로 성장 중인 기본 엔딩이다. |

### 8.1 엔딩 표시 공통 규칙

- 네 엔딩 모두 “수습 통과”로 마무리해 5분 플레이 후 허탈한 완전 실패를 피한다.
- `조용한 생존자`는 가장 낮은 등급이지만 조롱하지 않고 구체적인 성장 포인트를 알려준다.
- 엔딩 문구는 실제 인사평가 조언으로 오해되지 않도록 가볍고 가상적인 톤을 유지한다.

