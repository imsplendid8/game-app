# AI 스터디 공유자료 — 신입사원 김넵 키우기 기획 과정

> 이 문서는 `ai-study-kimnep-planning.pptx`의 텍스트 원본이다. 발표 대상은 AI 도구로 제품을 기획·구현하려는 내부 스터디 팀원이며, 발표 시간은 12~15분을 권장한다.

## Slide 1. 신입사원 김넵 키우기

**AI와 함께 5분짜리 선택형 게임을 기획한 방법**  
정답 퀴즈를 넘어, 다시 누르고 싶은 직장 메신저 시트콤으로

- AI 스터디 내부 공유
- Product planning case study

발표 메모: 결과물 소개보다 “어떤 결정을 AI에게 맡기고, 무엇을 사람이 확정했는가”에 초점을 맞춘다.

## Slide 2. 시작점: 한 문장과 11개 산출물

**입력**

- 회사의 애매한 표현을 해석하는 신입사원 시뮬레이션
- 모바일 웹, 5분, 문제 15개, 엔딩 4개
- 서버·회원가입·AI API 없이 먼저 완주 가능

**요청 산출물**

- PRD부터 게임 규칙, 데이터 구조, 개발 체크리스트, 구현 프롬프트까지

**핵심 제약**

- 실제 인물·회사·부서명 금지
- 비개발자가 이후 Claude Code로 구현
- 기능을 과도하게 늘리지 않기

발표 메모: 좋은 결과의 출발은 긴 아이디어가 아니라 우선순위가 드러나는 제약 조건이었다.

## Slide 3. 기획 순서: 재미보다 먼저 완주 구조

1. **플레이 약속:** 5분 안에 수습평가까지 간다.
2. **코어 루프:** 메시지 → 선택 → 즉시 후폭풍 → 수치 변화
3. **세션 구조:** 하루 3문제 × 5일 = 15문제
4. **피드백:** 일일 리포트와 최종 엔딩
5. **복귀:** 선택 직후 localStorage 저장

**왜 이 순서인가?**  
화면이나 캐릭터부터 정하면 기능이 늘어난다. 먼저 한 판의 시작·반복·종료를 고정하면 무엇을 만들지보다 무엇을 버릴지가 선명해진다.

## Slide 4. 사람이 확정한 결정 vs AI가 확장한 영역

| 사람이 확정 | AI가 초안을 확장 |
|---|---|
| 5분, 15문제, 4엔딩 | 화면별 세부 구성요소 |
| 5개 능력치 | 저장 상태 필드와 예외 흐름 |
| 서버와 실제 AI 제외 | 계산식과 경계값 후보 |
| 특정 회사명 금지 | 문항 소재와 결과 문구 후보 |
| 범위를 늘리지 않기 | 개발 순서와 검수 항목 |

**원칙:** AI는 빈칸을 빠르게 채우고, 사람은 취향·윤리·우선순위·최종 범위를 결정한다.

발표 메모: AI가 제안한 수치를 그대로 믿기보다 충돌 조건과 도달 가능성을 사람이 검증해야 한다.

## Slide 5. 첫 기획의 문제: 완성도와 재미는 다르다

**잘된 점**

- 화면·규칙·저장·엔딩이 연결된 완결된 사양
- 개발자가 임의로 결정할 부분이 적음
- 실제 AI 없이도 동작하는 구조

**아쉬운 점**

- 문항 제목이 교육 체크리스트처럼 보여 결과가 예상됨
- 최선 선택지만 유난히 길고 완벽해 보일 위험
- 캐릭터가 “정적인 회사원 아바타” 수준이라 고유 실루엣이 없음

**교훈:** 논리적 사양 검증과 감정적 플레이테스트는 별개의 단계다.

## Slide 6. 리프레시 원칙: 예절 퀴즈 → 선택형 시트콤

**기존 구조**  
상황 설명 → 올바른 답 찾기 → 교훈

**새 구조**  
3초 훅 → 애매한 회사어 → 서로 다른 유혹 → 짧은 후폭풍

**문항을 재미있게 만드는 세 장치**

1. 읽음 1, 입력 중…, 17:47, 최종_진짜최종 같은 디지털 디테일
2. 황당하지만 실제 감정에서 출발한 선택지
3. 정답/오답 대신 센스/무난/아쉬움/위험의 온도 차이

## Slide 7. 15문제는 유지하고 감정 곡선을 설계

| Day | 감정 테마 | 대표 에피소드 |
|---|---|---|
| 월 | 첫인상과 말투 | 단톡방 99+, 네넵넵! 과다 복용 |
| 화 | 불확실성 버티기 | 잠깐 이야기, 회의 자동 끄덕임 |
| 수 | 애매한 요청 구체화 | 5분 수정, 임팩트 버튼, 읽음 1 |
| 목 | 책임과 우선순위 | 파일 속 범인, 마감 두 개, 약어 왕국 |
| 금 | 관계와 퇴근 | 아무거나 점심, 17:47 알림, 수습 회고 |

**설계 포인트:** 학습 항목을 나열하지 않고 “월요일의 긴장 → 금요일의 평가”라는 한 주의 서사에 얹었다.

## Slide 8. 캐릭터 리프레시: 회사원이 아니라 메신저 생명체

**한 줄:** 메신저 이모지가 살아 움직이는 말랑한 신입사원 생존 코미디

- 2.5등신 젤리 실루엣과 둥근 사각형 얼굴
- 감정에 따라 `N`, `!`, `?`, 배터리로 변하는 안테나
- 라임 후드와 네이비 사원증 스트랩
- 점눈·한 줄 입·로딩 점 눈물
- 잉크 네이비, 라임, 민트, 코랄, 크림의 5색 체계

**하지 않는 것:** 검정 정장, 넥타이, 빌딩 숲, 상승 화살표, 기업용 스톡 벡터, 기존 캐릭터 모방

발표 메모: 48px 아바타에서도 실루엣이 읽히는지가 디테일의 화려함보다 중요하다.

## Slide 9. 규칙은 단순하게, 결과는 풍부하게

- 능력치 5개 모두 50에서 시작, 항상 0~100
- 선택 한 번의 변화량은 능력치별 -10~+10
- 랜덤·콤보·중도 게임오버 없음
- 같은 선택은 언제나 같은 결과
- 엔딩은 위에서 아래로 최초 일치하는 조건 하나 적용

**왜?**  
5분 게임에서 재미는 복잡한 수식이 아니라 선택의 맥락과 즉시 보이는 후폭풍에서 나온다. 단순한 규칙은 밸런스 검증과 AI 생성 콘텐츠 검수도 쉽게 만든다.

## Slide 10. AI 연결은 기능이 아니라 경계부터

**v1**

- 로컬 문제 데이터
- localStorage 진행 저장
- 규칙 기반 `localAnalyzer`

**추후**

- 같은 `GameAnalysis` 결과 형태를 반환하는 `openAiAnalyzer`
- 화면 컴포넌트는 분석 방식이나 API를 모름
- API 키는 브라우저나 저장 데이터에 두지 않음

**교훈:** 지금 쓰지 않을 API를 미리 구현하지 말고, 나중에 교체할 접점만 작게 만든다.

## Slide 11. 검증 루프: 문서도 테스트한다

**구조 검증**

- 요청한 11개 장이 모두 있는가?
- 15문제·4엔딩·5능력치가 서로 모순되지 않는가?
- 저장 복귀와 중복 선택 방지가 정의됐는가?

**재미 검증**

- 첫 두 문장에 장면이 보이는가?
- 두 선택지 이상이 실제로 고민되는가?
- 다른 결과도 보고 싶은가?
- 조롱 없이 웃긴가?
- 힌트를 하나 얻는가?

**운영 검증:** 3명 이상이 5점 척도로 평가하고 평균 3점 미만 문항은 다시 쓴다.

## Slide 12. 팀이 바로 써볼 수 있는 프롬프트 패턴

```text
역할: 모바일 선택형 게임의 콘텐츠 디자이너
목표: [문항 수]를 유지하면서 결과를 다시 보고 싶은 시트콤형 문항으로 개선
고정: 플레이 시간, 능력치, 엔딩 수, 기술 범위
변경 가능: 훅, 제목, 선택지의 유혹, 결과 리액션, 캐릭터 표현
금지: 실제 회사명, 특정 집단 조롱, 유행어 의존, 정답만 긴 선택지
출력: 변경 이유 + 문항표 + 재미 검증 기준
검수: 조건 충돌, 도달 가능성, 모바일 길이, 다시 선택하고 싶은 정도
```

**중요:** “재미있게 해줘”만 요청하지 말고, 유지할 것·바꿀 것·금지할 것·검수 방법을 함께 준다.

## Slide 13. 다음 액션과 스터디 토론

1. 캐릭터 기준 시트 1장을 먼저 만들고 48px 축소 검수
2. 15문제의 실제 선택지와 결과 문구 작성
3. 내부 3인 블라인드 재미 평가
4. 최저 점수 문항 3개만 다시 쓰기
5. Claude Code로 MVP 구현 후 5분 완주 테스트

**토론 질문**

- 우리 프로젝트에서 사람이 절대 위임하면 안 되는 결정은 무엇인가?
- 논리적으로 맞지만 재미없는 AI 결과를 어떻게 빨리 발견할까?
- 다음 반복에서 무엇을 추가하는 대신 무엇을 더 잘 삭제할까?

발표 메모: 산출물을 한 번에 완성했다고 보기보다, 구조 검증과 취향 검증을 분리한 두 번째 반복이 필요하다는 점으로 마무리한다.
