WithDKIS 시스템 설계

아이와 함께 참여할 수 있는 공공기관, 박물관, 과학관, 기업 공장견학 등의 저가·무료·희소 체험 프로그램을 발견하고, 선착순 접수 시작일을 놓치지 않도록 추적하는 개인용 예약 시스템입니다.

🎯
핵심 원칙
사용자의 관심사는 "어디서 할 수 있는가"가 아니라 "언제 신청할 수 있는가"입니다.

이 시스템이 추적하는 것

  • 박물관 도슨트 프로그램 - 저가 또는 무료
  • 공공기관 교육 프로그램 - 선착순 모집
  • 기업 공장견학 - 서울우유, 삼성 등
  • 과학관 실험 프로그램 - 정기 및 특별 프로그램
  • 방송국/기업 견학 - 제한된 정원
  • 공공 체험시설 - 선착순 예약
  • 특정 기간 모집 프로그램 - 방학 특별 프로그램

각 프로그램이 저장하는 정보

📋 필수 데이터 필드
  • 기관명, 프로그램명, 설명
  • 공식 URL, 실제 예약 URL
  • 체험일, 접수 시작/종료 날짜와 시간
  • 예약 방식 - 선착순, 추첨, 상시
  • 정원/잔여석, 가격
  • 대상 연령/학년, 보호자 동반 여부
  • 프로그램 상태 - UNKNOWN, OPENING_SOON, OPEN, CLOSED
  • 발견일/마지막 확인일

핵심 컴포넌트

1️⃣ Experience Management Service

체험 프로그램 CRUD 및 상태 관리

  • createExperience() - 신규 프로그램 등록
  • updateExperience() - 프로그램 정보 업데이트
  • updateRunStatus() - 특정 접수 회차 상태 변경
  • getExperiencesByDeadline() - 시간 기반 필터링
2️⃣ Crawler / Watcher Service

정기적으로 외부 사이트 확인 및 변화 감지

감지 항목:

  • 신규 체험 프로그램 생성
  • 접수 상태 변경 (OPENING_SOON → OPEN → CLOSED)
  • 접수 시간 공개
  • 정원/잔여석 변화
  • 가격 변화
  • 취소표 발생, 프로그램 취소
3️⃣ Pattern Analyzer Service

과거 프로그램 패턴 분석 및 다음 접수일 예측

분석 대상:

  • 반복 주기 (매월, 매주, 특정 요일)
  • 접수 시간 (월요일 10시, 1일 9시 등)
  • 체험일 기준 상대 시간 (체험 14일 전 등)
  • 계절성 (방학, 특정 시즌)
4️⃣ Adapter Framework

사이트별 크롤러 (Playwright 확장 가능)

adapters/
├── seoul-public-service/
├── museum/
│   ├── national-museum.ts
│   └── seoul-museum.ts
├── science-center/
└── factory-tour/
    ├── seoul-milk.ts
    └── samsung-factory.ts
5️⃣ Change Detection Engine

프로그램 변화 감지 및 로깅

변화 유형:

  • PROGRAM_CREATED / PROGRAM_UPDATED
  • STATUS_CHANGED / BOOKING_OPENED
  • BOOKING_TIME_REVEALED
  • CAPACITY_CHANGED / PRICE_CHANGED
  • CANCELLATION_OCCURRED / PROGRAM_CANCELLED
6️⃣ Notification Service

사용자에게 중요한 이벤트 알림

우선순위 이벤트:

  1. CRITICAL 오늘 신청 시작
  2. HIGH 내일 신청 시작, 7일 이내 신청, 취소표 발생
  3. MEDIUM 신규 프로그램, 가격/정원 변화
  4. LOW 기타 업데이트

데이터베이스 스키마

👤 User Tables
  • users - 사용자
  • user_preferences - 사용자 선호도
  • user_bookmarks - 위시리스트/북마크
  • notifications - 알림

Experience와 ExperienceRun 분리의 이유

💡
정기 프로그램의 여러 회차 관리
"국립박물관 도슨트 프로그램"은 매달 여러 회차가 있으며, 각 회차마다 접수 시간이 다를 수 있습니다. Experience는 프로그램의 틀, ExperienceRun은 각 회차입니다.

핵심 설계 결정

1️⃣ 데이터 모델링

❌ 기존 방식: "장소" 중심 (박물관, 과학관 검색)

✅ WithDKIS: "모집 프로그램" 중심 (접수 시간, 패턴, 예측)

사용자가 원하는 것은 "어디서 할 수 있나"가 아니라 "언제 신청할 수 있나"입니다.

2️⃣ Booking 상태 머신
UNKNOWN
    ↓ (booking_open_at 공개됨)
OPENING_SOON
    ↓ (현재시각 >= booking_open_at)
OPEN
    ↓ (현재시각 >= booking_close_at OR 정원 찬 경우)
CLOSED
3️⃣ 메인 화면: 시간 기반 우선순위
  1. 🔴 오늘 신청 (ACTION_REQUIRED_TODAY)
  2. 🟠 내일 신청 (ACTION_REQUIRED_TOMORROW)
  3. 🟡 7일 이내 (COMING_SOON_7DAYS)
  4. 🟢 지금 신청 가능 (CURRENTLY_AVAILABLE)
  5. 💰 무료 (FREE_PROGRAMS)
  6. 💵 1만원 이하 (BUDGET_FRIENDLY)
  7. ⚡ 선착순 (FIRST_COME)
  8. 👧 아이 연령 맞춤 (AGE_MATCHED)
4️⃣ 패턴 학습 전략

신뢰도 점수 계산:

  • 1개 회차: 0.3 신뢰도
  • 2개 회차: 0.6 신뢰도
  • 3개 회차: 0.8 신뢰도
  • 5개+ 회차: 0.95+ 신뢰도

패턴이 반복되면 자동으로 다음 예상 접수 시간을 계산합니다.

5️⃣ 자동화 안전성

automation_status 필드로 각 프로그램의 자동화 가능 여부 표시:

  • AVAILABLE 자동 신청 가능
  • CAPTCHA_REQUIRED CAPTCHA로 자동화 불가
  • QUEUE_REQUIRED 대기열 우회 불가
  • MANUAL_REQUIRED 기타 이유로 수동 필요

TOS 준수: robots.txt 준수, rate limiting, CAPTCHA/대기열 우회 금지

구현 로드맵 개요

8-12주 동안 6개 Phase를 거쳐 단계적으로 구현합니다.

📅
총 기간: 8-12주
각 Phase는 구체적인 Tasks, 테스트 전략, Success Criteria를 포함합니다.

단계별 구현 계획

Phase 1: 기초 인프라

기간: 주 1-2

목표: 기본 API 및 웹사이트 구축

  • 프로젝트 구조 생성
  • PostgreSQL 스키마 구현
  • REST API 기본 endpoints
  • 프론트엔드 기본 화면

산출물: 수동으로 입력한 프로그램을 웹에서 조회 가능

Phase 2: 크롤러 구축

기간: 주 3-4

목표: 자동 데이터 수집 및 변화 감지

  • Crawler 기본 구조
  • Change detection 엔진
  • First adapter (실제 사이트)
  • Crawl history 추적

산출물: 웹사이트에서 프로그램 자동 수집 및 변화 감지

Phase 3: 패턴 분석

기간: 주 5-6

목표: 접수 시간 예측

  • Pattern analyzer service
  • 과거 데이터 분석
  • 예측 엔진
  • 정확도 추적

산출물: 80% 이상 신뢰도로 접수 시간 예측

Phase 4: 스마트 알림

기간: 주 7-8

목표: 사용자 알림 및 대시보드

  • 사용자 관리 (인증)
  • Notification service
  • Email/Push 알림
  • 타임라인 대시보드

산출물: 사용자가 중요한 신청 시간을 놓치지 않음

Phase 5: 고급 크롤러

기간: 주 9-10

목표: 데이터 커버리지 확대

  • 2-3개 추가 adapter
  • 검색/필터링 개선
  • Analytics 및 리포팅
  • 사용자 피드백 반영

산출물: 5개+ 기관, 100개+ 프로그램 데이터

Phase 6: 자동화 기초

기간: 주 11-12

목표: Playwright 구조 설계

  • 자동화 가능성 분석
  • Playwright 구조 설계
  • 안전성 및 이용약관
  • 테스트 구조

산출물: Phase 7에서 실제 자동화 가능한 구조

Phase 7+: 완전 자동화 (미래)
  • 자동화 허용 사이트부터 실제 예약 구현
  • 사용자별 예약 우선순위 설정
  • 실패 시도 재시도 로직
  • 모니터링 및 로깅
  • 규정 준수 감시 (이용약관 등)

기술 스택

🖥️ Backend
  • Runtime: Node.js v18+
  • Framework: Nest.js (모듈성, 테스트 가능성)
  • ORM: TypeORM or Prisma
  • Database: PostgreSQL
  • Job Queue: Bull (스케줄된 크롤러)
  • Caching: Redis (크롤러 상태, 패턴 캐시)
🎨 Frontend
  • Framework: Next.js 14+
  • UI: React 18+, Tailwind CSS
  • State: TanStack Query (데이터 페칭)
  • Date: Day.js or date-fns
🕷️ Crawler
  • Static HTML: Cheerio
  • JavaScript-heavy: Playwright (미래)
  • Headless Browser: Puppeteer (대체)
🚀 Infrastructure
  • Containerization: Docker
  • CI/CD: GitHub Actions
  • Hosting: Vercel (Frontend), Railway/Heroku (Backend)

성공 지표

Phase Success Criteria
Phase 1 수동 입력한 3-5개 프로그램을 웹에서 조회 가능
Database schema 완전 구현
Phase 2 한 사이트에서 프로그램 자동 수집 성공
변화 감지 정확률 > 95%
Phase 3 80%+ 확신도로 접수 시간 예측 가능
예측 정확률 > 70%
Phase 4 사용자가 임박한 접수 시간을 놓치지 않음
알림 오픈율 > 50%
Phase 5 5개 이상 기관의 프로그램 수집
총 100개+ 프로그램 데이터베이스
Phase 6 자동화 구조 설계 완료
자동화 가능/불가 구분 로직 완성
